# Living Valley：AI 游戏导演设计

## 1. 项目定位

Living Valley 不是一个等待玩家提问的聊天助手，而是一个嵌入《星露谷物语》正常游玩过程的 AI 游戏导演。它观察玩家已经发生的游戏行为，在不打断操作的前提下，于后续游戏日生成并注入个性化信件、任务、NPC 对话和奖励，再根据玩家是否完成任务决定后续反馈。

项目的唯一核心创新是：**让游戏世界主动记住并回应玩家行为。**

第一阶段不扩展通用 Agent 平台，不建设新的 RAG、MCP 或多 Agent 框架，也不追求覆盖所有 NPC 和玩法。MVP 只完成一条稳定、可回放、可评测的动态任务链。

## 2. 为什么选择这个方向

现有仓库已经包含 Java/Spring AI、Vue、游戏知识数据和生成式能力，但主要交互仍是网页问答、推荐和图片分析。它和真实游戏过程分离，难以证明 AI 对玩家体验产生了实际影响。

本方案把生成能力放进游戏循环：

1. 玩家按照原有方式游玩，无需输入提示词；
2. 系统从真实行为中判断值得回应的时刻；
3. AI 生成符合角色性格和当前游戏状态的事件；
4. 确定性规则阻止不可执行或破坏平衡的内容；
5. 事件被写回游戏，完成结果继续影响下一次生成。

相比“NPC 长期记忆”或“截图攻略助手”，动态任务链同时具备可见的产品效果、明确的 Agent 决策过程和可自动测试的约束边界，因此更适合同时支撑 Agent 开发与测试开发岗位。

## 3. MVP 游戏体验

### 3.1 演示场景

MVP 聚焦威利和钓鱼行为：

1. 玩家在雨天前往海滩并连续钓鱼；
2. SMAPI Mod 记录日期、天气、地点、钓鱼次数、鱼类、等级和背包摘要；
3. 当天结束时，事件摘要被提交给游戏导演；
4. 次日早晨，威利寄来一封与昨日经历有关的个性化信件；
5. 一条符合当前季节、天气和玩家等级的限时挑战进入任务栏；
6. 玩家完成目标后获得受控奖励，并触发威利的后续对话；
7. 完成或失败结果被记录，成为下一次事件的上下文。

### 3.2 玩家可感知的创新

- 不打开聊天框，事件由游戏行为自然触发；
- 信件会引用玩家上一日的真实行为，而不是固定模板；
- 任务目标会随季节、等级和已捕获鱼类变化；
- AI 候选内容必须通过规则校验后才能进入存档；
- 同一个事件可以被完整回放，解释“为什么触发、为什么被修改、最终注入了什么”。

### 3.3 非目标

- 第一阶段不覆盖所有 NPC；
- 不生成新地图、新贴图或复杂动画；
- 不允许模型直接修改金钱、背包或存档文件；
- 不把现有 Web 聊天页面作为核心 Demo；
- 不依赖线上数据库才能完成现场演示。

## 4. 总体架构

### 4.1 C#：游戏接入层

新增 `stardew-director-mod/`，基于 SMAPI 实现：

- 监听 `DayStarted`、`DayEnding`、钓鱼、位置变化和任务完成事件；
- 将原始游戏对象转换成稳定的 `GameplaySnapshot`；
- 从 Go Runtime 拉取已验证事件；
- 使用 SMAPI/Content Patcher 能力注入信件、任务、对话和奖励；
- 上报注入、完成、失败和取消结果；
- 服务不可用时静默降级，不阻塞存档加载和正常游戏。

C# 层只负责采集和执行，不调用模型，也不自行决定剧情。

### 4.2 Java：剧情导演

在现有 `aurora-mcp` 中新增独立的 `director` 包，逐步将其定位为 `director-service`：

- 接收经过归一化的玩家状态和近期事件；
- 判断本次是否值得生成剧情；
- 生成严格符合 JSON Schema 的 `NarrativeEventCandidate`；
- 根据 Go 返回的违规原因进行最多一次修正；
- 模型不可用时使用固定种子的模板生成器，保证 Demo 可运行。

Java 层负责“有趣和个性化”，不拥有最终执行权。

### 4.3 Go：运行时与规则裁判

新增 `director-runtime/`，作为游戏与生成服务之间的稳定边界：

- 接收快照并按 `saveId + gameDate` 幂等去重；
- 调用 Java 剧情导演；
- 校验 NPC、季节、天气、鱼类、任务数量、奖励上限和前置条件；
- 对不合法候选返回机器可读的违规列表；
- 修正仍失败时选择安全模板，而不是把错误内容交给游戏；
- 使用嵌入式 SQLite 保存决策轨迹和回放数据；
- 提供 `replay` 命令，对历史输入重新执行规则并比较结果。

Go 层负责“确定、快速、可回放”，不负责自由文本创作。

### 4.4 共享契约

新增 `contracts/`：

- `gameplay-snapshot.schema.json`：玩家状态和行为摘要；
- `narrative-event.schema.json`：候选及最终事件；
- `violation.schema.json`：规则违规；
- `trace.schema.json`：生成、修正、注入和完成轨迹。

三个运行时都从同一份契约生成或校验 DTO，避免字段含义漂移。

## 5. 核心数据流

1. C# 在游戏日结束时生成快照并发送给 Go；
2. Go 校验输入、去重并创建 `traceId`；
3. Go 调用 Java 生成候选事件；
4. Go 执行确定性规则校验；
5. 若失败，Java 根据违规列表修正一次；
6. 若再次失败，Go 使用安全模板；
7. C# 在次日开始时拉取最终事件并注入游戏；
8. C# 上报注入结果和任务最终状态；
9. Go 将整条链路保存为可回放 Trace。

每个阶段都携带相同 `traceId`，面试演示时可以从一次游戏行为追踪到最终任务。

## 6. 规则边界

MVP 只实现与演示场景直接相关的规则：

- NPC 必须存在且本期只允许威利；
- 目标鱼必须在当前季节和地点可获得；
- 任务数量必须大于 0 且不超过配置上限；
- 奖励金币和好感度不得超过配置上限；
- 任务期限必须晚于创建时间；
- 同一存档同一游戏日最多创建一个导演事件；
- 已完成或已失效事件不得重复注入；
- 任何未知字段、未知物品和非法枚举都直接拒绝。

规则数据先放在版本化 YAML 中，避免 MVP 依赖仓库中缺失的数据库初始化文件。后续再决定是否接入完整游戏数据库。

## 7. 错误处理与降级

- Java 超时或不可用：Go 选择固定种子的安全任务模板；
- 模型返回非 JSON：记录原始响应摘要并进入一次修正；
- 两次校验失败：不注入候选内容，使用安全模板；
- Go 不可用：C# 跳过当日导演事件，不影响游戏；
- 重复请求：返回同一事件，不重复生成和发奖；
- 注入失败：C# 不写奖励，记录失败并允许下一游戏日重试；
- 存档切换：所有状态按 `saveId` 隔离。

系统遵循“宁可当天没有新事件，也不能破坏正常存档”的原则。

## 8. 测试与评测

### 8.1 自动化测试

- Go：规则表驱动单测、幂等测试、状态迁移测试；
- Java：结构化输出解析、一次修正、模板降级测试，模型通过 Stub 替代；
- 契约：三端 DTO 对 JSON Schema 的兼容性测试；
- C#：快照映射、事件应用和重复奖励保护测试；
- 回放：保存的 Trace 在相同规则版本下必须产生相同判定；
- 故障注入：超时、非法 JSON、未知鱼类、超额奖励和重复事件。

### 8.2 实现后再采集的指标

以下指标必须通过测试或 Demo 日志真实生成，未测量前不得写入简历：

- 候选事件 Schema 首次通过率；
- 规则首次通过率；
- 一次修正成功率；
- 安全模板降级率；
- 重复事件拦截率；
- 游戏内注入成功率；
- 端到端生成延迟 P50/P95；
- 回放一致率。

## 9. 安全与仓库基线

正式开发前必须先处理当前仓库的安全和可复现问题：

- 立即撤销并轮换已提交的 AI、MySQL 和 Redis 凭据；
- 配置全部改为环境变量，提交 `.env.example`；
- Go 与 Java 默认只监听本机地址；
- 移除未经校验的动态表名和列名 SQL；
- 不再依赖公网个人数据库完成 Demo；
- README 明确三个进程的启动顺序与版本要求。

## 10. 仓库规划

```text
Stardew-Sage/
├── stardew-director-mod/       # C# / SMAPI 游戏事件采集与内容注入
├── director-runtime/           # Go / 规则校验、幂等、轨迹与回放
├── aurora-mcp/                 # Java / Spring AI 剧情生成服务
├── contracts/                  # 跨语言 JSON Schema
├── demo/
│   ├── fixtures/               # 可重复输入
│   ├── traces/                 # 脱敏回放样例
│   └── scripts/                # 一键演示脚本
└── aurora-ui/                  # 非 MVP：后续可增加轨迹查看页
```

现有 `aurora-admin` 不进入第一阶段主链路，避免缺失内部依赖拖慢核心 Demo。

## 11. 实施阶段

### Phase 0：安全与可运行基线

清理凭据、补充环境变量示例、固定 Java/Node/Go/.NET 版本，并保证现有 Java AI 服务和前端可独立构建。

### Phase 1：契约与 Go Runtime

定义跨语言 Schema，实现规则校验、幂等、SQLite Trace 和命令行回放；先用固定候选事件跑通。

### Phase 2：Java 剧情导演

实现结构化生成、一次修正和离线模板降级，接入 Go Runtime。

### Phase 3：SMAPI 游戏闭环

采集雨天钓鱼行为，注入威利信件、任务、完成对话与奖励，并上报结果。

### Phase 4：演示与证据

准备固定存档或调试指令、录制 2—3 分钟 Demo、保存 Trace、运行自动化评测并形成真实指标。

## 12. Demo 脚本

1. 加载准备好的雨天存档；
2. 在海滩完成若干次钓鱼并结束当天；
3. 展示 Go Trace 中捕获到的行为摘要；
4. 次日读取威利个性化来信，并在任务栏看到动态任务；
5. 展示一条被规则拒绝并自动修正的候选事件；
6. 使用调试指令完成任务，展示后续 NPC 对话和奖励；
7. 运行回放命令，证明相同输入在相同规则版本下得到相同判定。

## 13. 简历证据目标

实现完成后，同一项目形成两套真实叙事：

- Agent 开发版：重点描述行为状态建模、结构化剧情生成、规则反馈修正、离线降级和跨语言契约；
- 测试开发版：重点描述规则表驱动测试、故障注入、幂等保障、Trace 回放和端到端质量指标。

所有数字只使用仓库测试报告和 Demo Trace 中可以复现的数据。用户独立完成的模块、既有仓库代码和后续协作贡献分别记录，不把原仓库已有能力包装成个人从零开发成果。

## 14. MVP 完成标准

- 玩家不使用聊天框也能触发完整事件；
- 雨天钓鱼行为能在次日生成并注入威利任务；
- 至少一次非法候选能被规则发现并完成修正或降级；
- 重复提交不会重复创建任务或发放奖励；
- Java 不可用时游戏仍可正常运行；
- 一条完整 Trace 可以被离线回放；
- Java 服务、Go Runtime 和前端构建命令可在 README 中复现；
- 仓库不再包含有效明文凭据。
